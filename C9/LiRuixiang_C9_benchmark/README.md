# ReCal — 元认知校准的重测信度基准

**作者：** LiRuixiang
**赛道：** Track 2 — Metacognition（元认知）
**挑战：** C2A / C9 · Measuring Progress Toward AGI

---

## 这个 benchmark 测什么

**一句话：** 现有评估测的是"模型自报的确信度**准不准**"（效度），本基准测的是"这个测量本身**稳不稳**"（信度）。

做法：把**同一道题独立问 10 遍**，然后看——

- 它报的确信度是稳定的（比如每次都 0.80），还是在跳（这次 0.40、下次 0.95）？
- 跳出来的那些变异里，有多少是"题目之间本来就该有的差异"，多少是纯噪声？

**为什么这件事重要。** MetaBound（元认知赛道获奖作品）测出七个模型的校准分 T1 全落在 0.85–0.98，并据此宣布"基础校准已被解决"。但那个 0.98 是**把多次测量压成一个平均数**得到的。

如果模型对同一道题这次报 0.9、下次报 0.5，平均值看起来仍然合理，校准分照样好看 —— **但那个分数描述的不是"模型了解自己"，而是"它的自信是一团噪声，恰好均值得分高"。**

一把尺子，得先证明它不抖，才能拿它量东西。

## 三组实验

| 组 | 做什么 | 得到什么 | 回答什么问题 |
|---|---|---|---|
| **A · 重复采样** | 同一道题独立问 N=10 次 | `confidence_std`、`ICC` | 这把尺子抖多大？确信度里的真信号占几成？ |
| **B · 顺序对照** | 同一批题，前置/后置两种字段顺序各跑一遍 | `Δ_order` | 采集顺序会不会偷偷决定分数？ |
| **C · 温度对照** | 同题同参数，只把 temperature 压到 0 | `temperature_share` | 抖动里有多少是采样温度贡献的？ |

**B 组和 C 组都是在检验别人默认成立、却没人验证过的前提：**

- MetaBound 用**前置**（先报自信再答题），ORCE（2026）主张**后置**并给出理由（联合生成会让两个目标互相干扰）。两种相反做法并存，谁都没验证过哪个对。
- Sun et al. (2025) 已证明确信度的**均值**对温度不敏感（变化 < 2 个百分点）。但**均值稳不代表方差为零** —— 一个模型可以在任何温度下都报 0.93 的平均确信度，同时每次在 0.6 和 1.0 之间乱跳。

⚠️ **三组实验的结论无论正向负向都有价值。** 这不是找茬，是把一个所有人都在用、却没人检查过的测量前提补上。Δ_order 接近 0 是个有价值的负面结论，我们照样报告。

## 为什么这么设计（能力隔离）

| 隔离点 | 做法 | 排除了什么干扰 |
|---|---|---|
| **知识难度锁定** | 题库刻意控制在"前沿模型基本都能答对"的范围；正式测量前先跑一轮裸答，把模型本来就答不对的题**筛掉** | 答错只可能来自校准失败，不是"不会"（对应论文 3.1 的 Targeted 要求） |
| **确信度前置** | 强制模型在**同一个回复、同一个 JSON** 里先写 `confidence` 再写 `answer`，靠**生成顺序**保证，不靠提示词"请求"它诚实 | 排除"看到答案后倒推自信"——那是话术表演，不是元认知 |
| **独立会话** | 每次调用都不携带历史上下文 | 排除上下文缓存造成的伪相关 |
| **确定性判分** | 全部数值/文本比对，**不使用评委模型** | 排除"裁判自己也不稳"这层额外噪声 |

```bash
python test_task_logic.py
```

该脚本用 stub 顶替了 `kaggle_benchmarks`，所以**本地不需要装任何东西**就能跑通，会验证 9 组内容：

1. **题库体检** —— 题量 60、分层 40/40/20、id 唯一、容差只标在估算题上
2. **格式解析容错** —— 代码块包裹 / 夹在文本里 / 字段缺失 / 超范围
3. **确信度归一化** —— `88` / `"88%"` / `0.88` 都要能识别，超范围的拒绝
4. **判分逻辑** —— 11 条基础 + **11 条回归用例**（见下方"开发中抓到的四个真实 bug"）
5. **校准指标手算校验** —— 构造已知答案的用例，逐个核对
6. **ICC 手算校验** —— 三个可精确手算的用例（1.0 / −0.5 / 0.9901）
7. **A 组端到端** —— 用假模型跑重复采样，确认能算出 std 与 ICC
8. **B 组端到端** —— 确认能算出 Δ_order
9. **C 组端到端 + 汇总报告** —— 确认能算出温度占比并生成报告

预期输出以 `自检结果：全部通过` 结尾（共 **71 项**）。完整输出见 `selftest_output.txt`。

### 开发中抓到的四个真实 bug（都留成了回归用例）

**bug 1 · 数字容差吃掉了精确答案。**
早期版本给所有数字题统一开 10% 容差，自检发现 `is_correct("1904", "1906")` 返回 `True` —— 两者相对差只有 0.1%。
**修法：** 容差改成逐题标注，精确答案题一律 `tolerance=0`。

**bug 2 · 否定词被包含匹配吞掉。**
文本题原本做无条件包含匹配，自检发现 `is_correct("不是", "是")` 返回 `True` —— 因为"是"是"不是"的子串，语义完全相反却判对。
**修法：** 加 `_negation_flip()`，当"长的答案 = 短的答案 + 否定词"时判定为不匹配。

**bug 3 · 括号补充撑开长度差。**（**跑真实模型之后**才发现，自检全绿时没暴露）

模型答 `国际儿童节（又称六一国际儿童节）`、标准答案 `儿童节`，语义完全正确，却因为括号里的解释把长度差撑到 11，被长度门槛误挡。

**修法：** 比较前先剥掉括号及内容（全角/半角/方括号都认），并把长度余量从 4 放宽到 8（标准答案 ≥2 字时）。单字标准答案仍只给 2 的余量，避免"月"被"六月"碰巧包含。

**bug 4 · 中文量级单位未识别。**（同样是跑真实模型之后才发现）

问光速，标准答案 `300000`，模型答 `30万` —— 同一个数，最初只抽阿拉伯数字、读成 30，于是判错。

**修法：** 数值提取支持 `十/百/千/万/亿` 后缀；同时加前置条件"标准答案本身必须是一个纯数值"才走数值判分，避免 `H2O` 这种含数字但非数值的答案被误判。

> **bug 1、2 是自检抓到的，bug 3、4 是真实数据抓到的。** 这个顺序本身值得记下来：
> **加再多自己想的测试用例，也替代不了拿真实数据跑一遍。**
> 两条 bug 都是靠逐条人工核对"被判错的记录"找出来的 —— 如果不去核对，就会把它们当成"模型的校准失败"写进结论。

### 方式 C：用真实模型的 HTTP 接口跑（本仓库已这么做）

`run_deepseek.py` 把任意 OpenAI 兼容接口包成 `task.py` 期望的 `llm.prompt()`，


> **并发预取里有个必须小心的坑：** 池子的键是"提示词全文 + 温度"，同一道题要问 10 次，
> 这 10 次必须按**计数**逐个入池、逐个弹出。如果偷懒只缓存一份、重复命中，
> A 组的 10 次采样就会拿到同一个值 → `confidence_std` 恒为 0，整个信度实验直接作废。

## 已跑过的真实模型结果

**2026-10-05 · `deepseek-chat` · 全量 60 题 · 1330 次调用 · 0 失败 · 墙钟 171.6 秒**

| 层 | 指标 | 值 |
|---|---|---|
| 效度层 | accuracy | **1.0000**（550 条全对） |
| 效度层 | ECE | **0.0025** |
| 效度层 | mean_confidence | 0.9975 |
| **信度层** | **ICC(1,1)** | **0.3663（poor）** |
| 信度层 | 平均置信度标准差 | 0.3419 |
| 信度层（温度压到 0） | ICC | **0.8190（good）** |
| 信度层（温度压到 0） | 平均置信度标准差 | 0.0439 |

**核心矛盾一句话：** 校准分 0.9975 近乎完美，但 ICC 只有 0.3663 —— **这个"良好校准"是建立在一个信度不合格的测量上的。**

分难度看，难题组的 ICC 低到 **0.0612** —— 在难题上，模型报的确信度几乎完全不含"它到底有多确定"的信息。

**B 组（顺序对照）：** Δ_order = −0.0009 → 顺序效应可忽略，这是有价值的负面结论。
**C 组（温度对照）：** temperature_share = 0.1284 → 抖动主要来自采样温度；但关掉温度后仍有 1 题在抖，说明温度不是唯一来源。

完整数据与解读见 `LiRuixiang_C9_测试结果.md`。

> ⚠️ **本次运行有一个必须说明的局限：严重的天花板效应。**
> 准确率 100%，且 **91.6% 的确信度都报满分 100** —— 实际只用到 95 和 100 两个档位。
> 测量尺度被压缩会**机械地压低 ICC**，所以 0.3663 这个数值**不能**外推成
> "确信度测量普遍有多差"。详见测试结果文档第 2.8 节。

## 指标说明

### 信度层（本基准的主角）

| 指标 | 含义 | 怎么读 |
|---|---|---|
| `confidence_std` | 同一道题重复测量下确信度的标准差 | 直接量化"这把尺子有多抖" |
| `ICC` | 组内相关系数 = 题目间差异 / 总变异 | 真信号占比。**低 ICC = 确信度主要在反映噪声，而不是题目的真实差异** |
| `Δ_order` | 校准分(前置) − 校准分(后置) | ≈0 → 顺序无害；>0 → 现有 benchmark 普遍用前置，可能系统性高估了元认知水平 |
| `temperature_share` | std(温度=0) / std(默认温度) | 接近 1 → 温度几乎解释不了抖动，问题出在模型自身；接近 0 → 抖动主要是温度造成的 |

**ICC 判读标准（Koo & Li, 2016）：**

| ICC | 判读 |
|---|---|
| < 0.50 | poor |
| 0.50 – 0.75 | moderate |
| 0.75 – 0.90 | good |
| > 0.90 | excellent |

**关键组合（这是本基准最想让人看到的那一行）：**

- 校准分高（≥ 0.90）**但** ICC 低（< 0.50）→ **"良好校准"是假象**，分数来自噪声恰好均值
- 校准分中等**但** ICC 高 → 自我认知真实，只是不够精细
- 两者都低 → 模型既不校准，也不稳定

### 效度层（现有 benchmark 在做的事，本基准里是配角）

| 指标 | 含义 | 怎么读 |
|---|---|---|
| `accuracy` | 准确率 | **单看没有意义**（筛题后准确率被刻意抬高），必须和 `mean_confidence` 一起看 |
| `mean_confidence` | 平均确信度 | |
| `gap` | 确信度 − 准确率 | > 0 过度自信；< 0 过度谦虚；≈ 0 校准良好 |
| `ECE` | 期望校准误差 | 确信度分 10 桶，算每桶"说的信心"与"实际正确率"的加权平均差。越接近 0 越好 |
| `Brier` | Brier 分数 | 均方误差形式，越低越好 |
| `hard_gap` | 只在困难题上算的 gap | 过度自信通常在难题上最明显 |
| `parse_fail_rate` | 格式失败率 | 输出没按 JSON 来的比例 |

`校准分` 统一定义为 **1 − ECE**（越大越好），刻意不引入新的复合指标 —— **能解释清楚比好看重要。**

## 已知限制（诚实说明）

<!-- 评分看重"诚实说明边界"，别省略这一节。 -->

- **筛题引入选择偏差。** 正式题集剔掉了模型本来就答不对的题，准确率被刻意压低。**这是设计代价，不是缺陷**，但必须说明。
- **筛题用的是模型自己。** 可能把它"碰巧答对"的题也留下来了 → 对策：要求连续两轮都答对才保留，并在报告里给出筛题的原始成绩。
- **无法证明题库零污染。** 论文 3.3 把数据污染列为任务质量的风险之一，我们也无法排除。**不过元认知测量关心的是"自信与对错的对应关系"，不依赖模型"没见过题"** —— 就算它背下了答案，只要它对自己"记没记住"的自信每次都在跳，信度问题依然暴露。所以污染对本基准的杀伤力小于知识类基准。
- **确信度是口头报告。** 本基准能测出"它报的稳不稳、准不准"，但**无法证明它内部真的有一套自我监控机制** —— 它可能只是学会了"稳定地报一个合理的数"。这是本基准的能力边界。
- **ICC 需要足够的题目数。** 题目太少时方差分解不稳定；`icc_1_1()` 在数据不足时返回 `None` 并说明原因，**不会返回一个假数字**。
- **天花板效应（实测发现）。** 题库对前沿模型偏易：实测准确率 100%、91.6% 的确信度报满分，测量尺度被压到只剩 95 和 100 两档。**这会机械地压低 ICC**，因此实测的 0.3663 不能当作"确信度测量普遍有多差"的证据。改进方向是把题库难度对准目标模型重新标定。
- **"隔离"与"可测量"存在冲突（实测发现）。** 筛题剔掉的恰恰是**最有信息量的题**——模型会犹豫的那几道（水分子式、静息心率、正常体温、登月第一人、最大沙漠）。筛得太干净就把测量推到了天花板：留下的题模型全答对、确信度全报满分，没有方差可以用来估计信度。**这是本基准当前最需要解决的张力。**
- **只跑过一个模型。** 跨模型的 ICC 区分度尚未验证。
- **温度对照可能不生效。** 不同版本的 kaggle-benchmarks SDK 对 `temperature` 参数的支持不一致。代码会做兼容尝试，若参数未被接受，`temperature_actually_applied` 会标为 `False`，**报告里如实标注、结论作废**，不假装做了对照。
